### v0.1

Первичная спецификация MVP.

## 1. Цель

Создать универсальный CLI-инструмент для временного и постоянного хранения информации AI-агентами.

Основные принципы:

- Агент работает с БД исключительно через CLI.
- Агент не знает физический путь к SQLite.
- Удаление записей через CLI запрещено.
- Не требуется MCP, HTTP API или отдельный сервер.
- Инструмент независим от конкретного AI-агента.

## 2. Архитектура

## 4. CLI-контракт

Бинарь: `agent-sqlite` (точка входа `agent_cli_sqlite.cli:main`).

### 4.1 Команды

```
# Сохранение (создание или обновление по (project, key))
agent-sqlite save \
  --project my-app \
  --key architecture \
  --value "FastAPI + SQLite" \
  [--scope persistent|temporary] \
  [--ttl SECONDS]

# Чтение по ключу
agent-sqlite get --project my-app --key architecture

# Поиск по содержимому и ключу
agent-sqlite search --project my-app --query "FastAPI" [--limit N]

# Список записей проекта
agent-sqlite list --project my-app [--limit N] [--scope persistent|temporary]
```

Обязательные опции: `save` — `--project`, `--key`, `--value`; `get` — `--project`, `--key`;
`search` — `--project`, `--query`; `list` — `--project`.

Опции: `--scope` (default `persistent`), `--ttl` (секунды, default `3600`, только при `--scope temporary`),
`--limit` (default: `search` — 50, `list` — 100; верхняя граница 1000).

### 4.2 Формат успешного ответа

Все команды печатают в stdout ровно один JSON-объект.

```jsonc
// save
{"ok": true, "project": "my-app", "key": "architecture", "scope": "persistent",
 "created": true, "expires_at": null, "updated_at": "2026-11-01T12:00:00Z"}

// get
{"ok": true, "record": {"id": 1, "project": "my-app", "key": "architecture",
 "value": "FastAPI + SQLite", "scope": "persistent",
 "created_at": "2026-11-01T12:00:00Z", "updated_at": "2026-11-01T12:00:00Z",
 "expires_at": null}}

// search
{"ok": true, "query": "FastAPI", "count": 2, "records": [ /* record-объекты */ ]}

// list
{"ok": true, "count": 3, "records": [ /* record-объекты */ ]}
```

Ключ `created` в `save` равен `true`, если запись создана, `false` — если обновлена существующая.

### 4.3 Формат ошибки

Ошибки печатаются в stderr одним JSON-объектом, stdout остаётся пустым:

```json
{"ok": false, "error": {"code": "not_found", "message": "key not found: architecture",
 "details": {"project": "my-app", "key": "architecture"}}}
```

Коды `error.code` (стабильный контракт, агенты могут ветвиться по нему):

| code              | Назначение                                        |
| ----------------- | ------------------------------------------------- |
| `validation_error`| Некорректные аргументы, нарушение форматов         |
| `not_found`       | Ключ отсутствует или запись истекла                |
| `storage_error`   | БД недоступна, повреждена, заблокирована           |
| `internal_error`  | Непредвиденная ошибка                             |

Ошибки `argparse` (неизвестная команда, отсутствующая опция) перехватываются и также
возвращаются в формате JSON с `code = "validation_error"` — штатный текст argparse не выводится.

### 4.4 Коды возврата

| Код | Значение                                              |
| --- | ----------------------------------------------------- |
| 0   | Успех                                                 |
| 1   | `internal_error`                                      |
| 2   | `validation_error` (в т.ч. ошибки разбора аргументов)  |
| 3   | `not_found`                                           |
| 4   | `storage_error`                                       |

## 5. Модель данных

### 5.1 `records`

| Поле        | Тип          | Назначение                                          |
| ----------- | ------------ | --------------------------------------------------- |
| id          | INTEGER      | Primary Key                                         |
| project     | TEXT         | Идентификатор проекта                               |
| key         | TEXT         | Ключ записи                                         |
| value       | TEXT         | Содермое                                            |
| scope       | TEXT         | `temporary` / `persistent`, CHECK-ограничение        |
| created_at  | TEXT         | Дата создания (ISO 8601 UTC)                         |
| updated_at  | TEXT         | Дата изменения (ISO 8601 UTC)                         |
| expires_at  | TEXT         | Время истечения TTL, `NULL` для persistent            |

Уникальность: `(project, key)`.

```sql
CREATE TABLE IF NOT EXISTS records (
    id         INTEGER PRIMARY KEY,
    project    TEXT NOT NULL,
    key        TEXT NOT NULL,
    value      TEXT NOT NULL,
    scope      TEXT NOT NULL CHECK (scope IN ('temporary', 'persistent')),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    expires_at TEXT,
    UNIQUE (project, key)
);
CREATE INDEX IF NOT EXISTS idx_records_project_updated ON records (project, updated_at DESC);
CREATE INDEX IF NOT EXISTS idx_records_expires ON records (expires_at);
```

### 5.2 `schema_meta`

```sql
CREATE TABLE IF NOT EXISTS schema_meta (version INTEGER NOT NULL);
```

Текущая версия схемы: `1`. Инициализация схемы выполняется автоматически при первом
подключении (`CREATE TABLE IF NOT EXISTS`). Повреждённая БД не пересоздаётся и не сбрасывается —
CLI возвращает `storage_error`.

### 5.3 Истёкшие записи

Запись считается истёкшей, если `expires_at IS NOT NULL AND expires_at <= now (UTC)`.
Истёкшие записи исключаются из `get`, `search` и `list` (для `get` — `not_found`),
но физически остаются в БД.

## 6. Безопасность

Ключевое требование: CLI не предоставляет возможности удаления данных.

- Отсутствуют команды `delete`, `clear`, `drop`, `truncate`, `reset`.
- Произвольные SQL-запросы запрещены.
- Путь к БД определяется внутренней конфигурацией инструмента (§12.3).
- CLI не раскрывает путь к БД в ответах и ошибках.
- SQL-запросы параметризованы.
- При обновлении запрещено изменять `project` и `key`.
- Skill прямо запрещает агенту искать, изменять или удалять файл SQLite.

Ограничение: скрытие пути не является полноценной изоляцией, если агент имеет неограниченный
shell-доступ от того же пользователя. Для строгой защиты потребуется отдельный системный
пользователь и разграничение прав ОС.

### 6.1 Границы защиты

Что гарантирует MVP (проверяется тестами `tests/test_security.py`):

| Угроза                          | Защита                                                          | Тест                                            |
| ------------------------------- | --------------------------------------------------------------- | ----------------------------------------------- |
| Удаление через CLI              | Команды `delete/clear/drop/truncate/reset` отсутствуют            | `test_no_delete_like_commands`                   |
| Произвольный SQL                | Нет SQL-passthrough, все запросы параметризованы                  | `test_raw_sql_passthrough_is_rejected`           |
| SQL-инъекция в значении         | Значение хранится литералом                                      | `test_sql_injection_in_value_is_stored_literally` |
| Утечка пути к БД               | Путь не выводится в stdout/stderr и не попадает в тексты ошибок   | `test_save_does_not_leak_path_on_success`, `test_storage_error_does_not_leak_path` |
| Сброс повреждённой БД           | При ошибке файл не перезаписывается                                | `test_corrupted_database_is_not_reset`           |
| Изменение `project`/`key`       | В `UPDATE` участвуют только `value/scope/updated_at/expires_at`   | `test_project_and_key_are_immutable_on_update`   |

Чего MVP **не** гарантирует: агент с неограниченным shell-доступом от того же OS-пользователя
способен удалить или перезаписать файл БД напрямую. Это свойство ОС, а не CLI: запрет
удаления возможен только при запуске CLI от отдельного сервисного аккаунта (§10.1).

## 7. Agent Skill

Файл: `skills/agent-cli-sqlite/SKILL.md`

Skill должен описывать:

- Когда сохранять информацию.
- Как выбирать `temporary` или `persistent`.
- Как формировать ключи.
- Как искать ранее сохранённый контекст.
- Как обрабатывать ошибки CLI (по `error.code` и коду возврата).
- Запрет прямого доступа к SQLite.

Правило: агент самостоятельно решает, что сохранить, но взаимодействует с памятью только
через разрешённые команды.

## 9. Acceptance Criteria

| Тест                       | Ожидаемый результат                          |
| -------------------------- | -------------------------------------------- |
| Сохранение persistent      | Запись сохраняется между запусками           |
| Сохранение temporary       | Запись получает TTL                          |
| TTL по умолчанию           | `--scope temporary` без `--ttl` → 3600 с      |
| `--ttl` со `persistent`    | `validation_error`, код возврата 2           |
| Истечение TTL              | Запись скрыта, но существует в БД            |
| Поиск                      | Возвращаются релевантные записи              |
| Поиск по чужому проекту    | Записи другого проекта не возвращаются      |
| Изоляция проектов          | Записи других проектов недоступны через CLI  |
| Команда delete             | Ошибка: неизвестная команда                  |
| Произвольный SQL           | Не поддерживается                            |
| Повторное сохранение ключа | Обновление значения без удаления записи       |
| `created` в ответе `save`  | `false` при обновлении существующего ключа    |
| Повреждение БД             | Понятная ошибка без автоматического сброса   |
| Формат ответа              | Ровно один JSON-объект в stdout               |
| Ошибка                     | JSON в stderr, пустой stdout, код ≠ 0        |

## 10. За пределами MVP

- MCP-сервер.
- HTTP API.
- Векторный поиск и embeddings.
- Синхронизация между машинами.
- Многопользовательский доступ.
- Автоматическое физическое удаление истёкших записей.
- Шифрование БД.
- FR-10: история изменений (отдельная таблица `record_history`, изменение `records` не требуется).
- Отдельная команда `update` (FR-09 покрыт upsert'ом в `save`).

### 10.1 Backlog следующей версии (по итогам ревью TL, 2026-11-01)

Не блокирует MVP.

- Резервное копирование БД (SQLite backup API / снапшот-файл) без нарушения запрета на удаление.
- Явная команда диагностики целостности (`PRAGMA integrity_check`) с JSON-отчётом.
- Защита от случайной перезаписи важных persistent-записей (например, подтверждение
  перезаписи или непригодные для перезаписи ключи).
- OS-изоляция как единственный способ запретить удаление данных при произвольном
  shell-доступе агента от того же пользователя (отдельный сервисный аккаунт + права на
  каталог/файл БД). Текущий MVP ограничивается только поверхностью CLI — см. §6.
  Схема реализации (spike): CLI запускается от отдельного сервисного пользователя
  (`sudo -u agentmem agent-sqlite ...` на Linux, отдельная локальная учётка + ACL на Windows),
  каталог БД недоступен агенту на запись. Важно: WAL создаёт `-wal`/`-shm` рядом с БД, поэтому
  запрет удаления применяется к файлу БД, а не к каталогу — иначе SQLite не сможет закрыть
  WAL-сегменты.

## 11. Критерий готовности

MVP считается готовым, когда агент способен самостоятельно сохранять и извлекать контекст
через терминал, использовать временную и постоянную память, а CLI не предоставляет операций
удаления.

Итоговое решение: один Python CLI, одна SQLite БД, один Skill. Минимум зависимостей и инфраструктуры.

## 12. Implementation Decisions

### 12.1 Обновление записей (FR-09)

Отдельная команда `update` не вводится. `save` — операция upsert по уникальному ключу
`(project, key)`:

- `INSERT ... ON CONFLICT(project, key) DO UPDATE SET value=..., scope=..., expires_at=..., updated_at=...`;
- `created_at` при обновлении не меняется;
- `project` и `key` неизменяемы по построению — в `DO UPDATE` они не участвуют;
- обновление считается изменением значения, а не удалением: строка в БД не пересоздаётся,
  `id` сохраняется.

Обоснование: «Обновление существующих записей» уже покрывается повторным `save` (§9), а
вторая команда с почти идентичной семантикой добавила бы второй путь к записи без новой
функциональности.

### 12.2 TTL-семантика (FR-05)

- Единицы: секунды, целое число, диапазон `1 <= ttl <= 2592000` (30 дней).
- `--scope temporary` без `--ttl` → TTL `3600` с (1 час).
- `--ttl` с `--scope persistent` → `validation_error` (опция неприменима, а не игнорируется).
- `expires_at` вычисляется как `now(UTC) + ttl` в момент записи.
- При повторном `save` TTL пересчитывается от момента сохранения (`expires_at` обновляется).
- `expires_at` хранится в ISO 8601 UTC (`YYYY-MM-DDTHH:MM:SSZ`).
- Значение `--scope` по умолчанию — `persistent`.

### 12.3 Путь к БД и конфигурация

- Переменная окружения `AGENT_SQLITE_DB` — переопределение пути (используется в тестах).
- Путь по умолчанию:
  - Windows: `%LOCALAPPDATA%\agent-cli-sqlite\memory.db`;
  - Linux/macOS: `${XDG_DATA_HOME:-~/.local/share}/agent-cli-sqlite/memory.db`.
- Каталог создаётся при первом подключении, если отсутствует.
- Путь не выводится ни в stdout, ни в stderr, ни в текстах исключений: все сообщения об
  ошибках БД обезличены (`storage_error` без пути).
- Одновременные вызовы CLI: `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout=5000`,
  `PRAGMA synchronous=NORMAL`.

### 12.4 JSON-контракт и коды возврата

- Успех: один JSON-объект в stdout, код возврата `0`.
- Ошибка: один JSON-объект в stderr, stdout пуст, код возврата соответствует §4.4.
- Стабильные имена полей и `error.code` — часть контракта; изменения требуют bump версии PRD.

### 12.5 Валидация

- `project`: `^[A-Za-z0-9._-]{1,64}$`.
- `key`: `^[A-Za-z0-9._:-]{1,128}$`.
- `value`: непустая строка; ограничения по длине нет.
- `--query`: непустая строка; `%` и `_` экранируются, используется `LIKE ... ESCAPE '\'`.
- `--limit`: целое `1..1000`.

### 12.6 Поиск и список

- `search` ищет по `value` **и** по `key`, регистронезависимо (ASCII-семантика `LIKE`).
- Поиск ограничен текущим `--project`.
- `search` сортирует по `updated_at DESC`, `list` — по `updated_at DESC`.
- `list` без `--scope` возвращает все видимые записи проекта; с `--scope` — только записи
  указанного scope.

### 12.7 История изменений (FR-10)

Вынесена за пределы MVP. Причина: FR-10 — P1, не влияет на критерий готовности (§11), а
реализация требует отдельной таблицы, ветки записи и отдельной команды. Схема это не
блокирует: история реализуется отдельной таблицей `record_history` без миграции `records`.

### 12.8 Прочее

- Имя бинаря — `agent-sqlite`; имя пакета — `agent_cli_sqlite`; имя проекта — `agent-cli-sqlite`.
- Версия схемы хранится в `schema_meta`; миграции — ручные, с bump `version`.
- Ошибки `argparse` перехватываются и приводятся к JSON-контракту (§4.3).
- Тесты: `pytest`, зависимость только для dev; runtime — только стандартная библиотека.
